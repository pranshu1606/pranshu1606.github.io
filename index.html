Distributed Order Processing

A microservices back end where an Order service and an Inventory service each own their PostgreSQL data and talk over REST — so an order is only placed when stock can actually be reserved. PostgreSQL makes every stock decision, so concurrent orders never oversell. Stock reads are cached in Redis, and the whole stack runs from one Docker Compose file, tested in GitHub Actions and with k6 load and chaos tests.

  • Database‑per‑service: separate PostgreSQL stores for orders and inventory
  • Service‑to‑service calls with Spring RestClient — check stock, then reserve it
  • Redis cache‑aside with @Cacheable, evicted the moment stock is reduced
  • Bean Validation with central handlers returning clean 400 / 404 / 409s
  • Concurrency‑safe: 10 parallel buyers against 5 units always yields exactly 5 orders
  • Failure‑safe orders: idempotent reservations, compensation, 503 + Retry‑After
  • Multi‑stage Docker images, gated by Actuator health checks
  • CI runs tests, builds both images and smoke‑tests the full stack on every push

What held upStock stayed exact in every run: 0 lost units and 0 duplicate orders through overload and a database outage. PostgreSQL decides each sale, so a stale cache can never cause an oversell.
What broke, and the fixFreezing the database for 8 seconds lost 135 units: Inventory finished reductions after Order had given up. Now each order carries a reservation ID, Order gives stock back exactly once and answers 503 “retry” quickly, and an Idempotency‑Key stops duplicate orders.
