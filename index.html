Distributed Order Processing

A microservices back end where an Order service and an Inventory service each own their PostgreSQL data and talk over REST — so an order is only placed when stock can actually be reserved. PostgreSQL makes every stock decision, so concurrent orders never oversell. Stock reads are cached in Redis, and the whole stack runs from one Docker Compose file and is tested in GitHub Actions and with k6 load and chaos tests.

  1. A client places an order.POST /orders reaches the Order service on :8080.
  2. Order asks Inventory.A service‑to‑service REST call with Spring RestClient.
  3. Each service owns its data.Separate PostgreSQL databases, with Redis caching stock reads.
  4. Check stock, then reserve it.PostgreSQL reduces stock atomically; the order is saved only if that succeeds.
  5. Bad requests fail cleanly.Field‑level 400s, plus clear 404 and 409 responses.

What held up

Stock stayed exact in every run: 0 lost units and 0 duplicate orders through overload and a database outage. PostgreSQL decides each sale, so a stale cache can never cause an oversell.

What broke, and the fix

Freezing the database for 8 seconds lost 135 units: Inventory finished reductions after Order had given up. Now each order carries a reservation ID, Order gives stock back exactly once and answers 503 “retry” quickly, and an Idempotency‑Key stops duplicate orders.

What’s next

Making that give‑back survive a crash (a reconciliation job or outbox), running several service replicas behind a load balancer, and re‑measuring on a dedicated machine.
